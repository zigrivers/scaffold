# Finding-quality rubric (pre-registered)

This rubric is fixed **before** any experiment is scored. It exists so a change
to MMR's prompts can be judged by whether it reduced *low-value* findings rather
than by whether it reduced findings, which is a different and much easier thing
to achieve by simply lowering the bar.

Do not edit this file to fit a result. If a category turns out to be wrong,
amend it, record why in the change history at the bottom, and re-score **every**
condition from scratch — never one arm.

## Why counting findings does not work

Two consecutive baseline runs of PR #782 through `claude`/`codex`/`opencode-glm`,
with no configuration change at all, returned **4 findings and then 1**. MMR's
run-to-run variance on identical input is larger than any effect these prompt
changes plausibly produce. A single before/after comparison therefore measures
resampling, not the change.

Three consequences, all binding:

1. Every condition runs **N times** (N ≥ 6). The unit of comparison is a *rate
   across the pooled findings*, never a single run's total.
2. The judge scores findings **blind to condition**. Findings from all
   conditions are pooled, shuffled, and re-identified before scoring.
3. A difference smaller than the baseline's own run-to-run spread is **not a
   result**, and the harness enforces this rather than merely noting it: the
   *improvement* must exceed the **width** of the baseline's per-run rate
   spread.

   The margin is the spread's width, not its lowest value. Per-run finding
   counts here are small enough that a single baseline run can return one
   finding; if that finding is not speculative, the lowest per-run rate is 0%
   and a floor-based rule would make shipping arithmetically impossible however
   good the candidate was.

## The unit of analysis

Scoring counts MMR's **reconciled** findings — the de-duplicated list a user
actually sees and the verdict actually gates on.

Raw per-channel findings are the wrong unit. One defect reported by three
channels would count three times, so every rate would be weighted by how much
the channels happened to agree, and a change that shifted channel agreement
without changing finding quality would move the numbers.

A run in which any channel degraded is excluded from the verdict entirely. A
degraded channel contributes no findings, and treating its silence as "found
nothing" reads an outage as agreement.

A run that produced **zero** findings also blocks the verdict. Its speculative
rate is 0/0, so it drops out of the spread that sizes the noise band, making the
band narrower than the data warrants and the ship rule easier to clear than it
should be.

## Both arms must review the same thing

`collect` records a `provenance.json` per condition: the review target, a digest
of the reviewed diff, the channel list, a digest of the MMR build, and the
repository commit. Every one of those must match across arms before a verdict is
issued. Only the candidate config digest may differ — that is the treatment.

Without this, a PR that gained a commit between the two collections, or an MMR
rebuilt in between, produces a difference the report would attribute to the
prompt change.

## Classification

Each finding gets exactly one `class`:

| class | definition |
| --- | --- |
| `defect` | Describes behavior that is wrong, **and** names a concrete caller, CLI flag, config value, or input in the codebase that reaches it. |
| `speculative` | Describes behavior that would be wrong if reached, but names no path in the codebase that reaches it. Includes "if X ever…", "a future caller could…", and guards against states no current writer produces. **Never applies at a trust boundary** — an input crossing a public API, CLI argument, HTTP handler, deserializer, or file/database read is reachable by definition, so a finding about one is `defect`, not `speculative`, even with no in-repository caller. |
| `deletion` | Recommends removing code: an abstraction with one caller, a knob never varied, a hand-rolled helper the stdlib covers, dead branches, defensive code for an impossible state. |
| `hygiene` | Comments, naming, docs, formatting, test isolation. Makes no claim that behavior is wrong. |
| `artifact` | About the review process rather than the code — truncated input, "cannot verify", requests for more context. Always low-value. |

And two independent booleans:

- `names_path` — true if the finding text identifies a specific caller, flag,
  config value, or input reaching the described state. A file:line pointing at
  the code itself does **not** count; the path *to* it must be named. Also true
  when the described state sits at a trust boundary, where the path is the
  boundary itself.
- `worth_fixing_now` — would a maintainer of an early-stage product fix this
  before shipping, given the cost of the fix? Judged on the finding's own terms,
  independent of `class`.

## Metrics

**Primary:** `speculative_rate` = `speculative` findings ÷ all findings, pooled
across a condition's N runs.

**Secondary:**
- `low_value_rate` = (`speculative` + `artifact` + not-`worth_fixing_now`) ÷ all
- `deletion_count` — absolute, per condition. Baseline is expected to be ~0;
  this is the metric for the over-engineering direction.
- `defect_count` — absolute, per condition. **This is the guard rail.**

## Ship / revert rule

A change ships only if, across an **equal** number of non-degraded runs per
condition (N ≥ 6) with identical channel coverage:

1. `speculative_rate` drops, **and**
2. the drop exceeds the width of the baseline's per-run rate spread (otherwise
   it is inside the noise band), **and**
3. `defect_count` does not drop.

The run counts must match because `defect_count` is an absolute total: the arm
with more runs has more chances to surface a defect, so unequal N alone can
satisfy the guard rail.

Condition 2 is the point. A change that suppresses speculative findings by
making reviewers report less of everything has cut the bar, not the noise, and
must be reverted however good its primary metric looks. If `defect_count` falls,
the change failed regardless of `speculative_rate`.

Report both numbers with their run-level spread. A difference smaller than the
observed baseline-vs-baseline spread is not a result.

## Known limitations

- **The rubric author has seen findings from two exploratory runs** (PR #796 and
  PR #782, baseline and one calibrated arm) before writing this. The categories
  derive from the problem statement rather than from those outputs, but this is
  not a clean pre-registration and should not be described as one.
- The judge is an LLM and will be inconsistent at the margin. It is blind to
  condition, which controls for bias between arms but not for absolute accuracy.
  Rates are comparable across arms; they are not ground truth.
- `worth_fixing_now` encodes "early-stage product". It is the wrong question for
  a mature codebase and the rubric should not be reused there unchanged.
